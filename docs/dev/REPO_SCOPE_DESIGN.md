# Repo Scope Design

**Status:** Implemented, experimental since 0.48.0 (`dtctl repo-scope`, `query --repo-scope` and `--no-repo-scope`, `verify query --repo-scope`, `wait query --repo-scope`, `--repo-scope` on the breakpoint commands)

Link a git repository to the entities that run its code, so that a developer, or an agent working in their checkout, can query "this code's" logs and spans without naming a service. User guide: [REPO_SCOPE.md](../REPO_SCOPE.md).

---

## Why not filter segments

Filter segments are how Dynatrace scopes a query, and `dtctl query` already takes `--segment`. An entry is not a segment for three reasons:

1. **Creating a segment is a write.** It needs `storage:filter-segments:write`, and linking a repository has to work for a developer with ordinary, read-only permissions. A repo scope is set up by reading (`discover`) and by writing a local file (`set`); nothing in the environment changes.
2. **A segment cannot express per-directory scope.** It is an environment object with one meaning wherever it is used. A monorepo needs a different filter depending on the directory a command runs from, which only the client knows.
3. **The link belongs with the code.** It is reviewed, versioned and branched with the repository, and every clone has it. A segment lives in the environment, outside that review.

None of the three is a reason not to *use* a segment that already exists, and an entry can name some: see [Segments an entry references](#segments-an-entry-references). Reading a segment needs no write scope, the entry still decides per directory, and the reference is reviewed with the code. dtctl never creates or changes one.

## dtui's workspace file

[dtui](https://github.com/dynatrace-oss/dtui) reads a second per-project file, `.dtui.yaml`: the environment to open, a timeframe, a start view, presets, and the filter segments it applies to every view. The two files stay separate, each owned by one tool, and compose by a fixed rule. Rule 1 describes dtctl as it is. Rules 2 to 5 describe the intended composition: dtui does not read the scope file yet (follow-up 19), and cannot until a dtctl release carries `pkg/reposcope`.

| | `.dtctl-repo-scope.yaml` | `.dtui.yaml` |
|---|---|---|
| Owner | dtctl (`pkg/reposcope`) | dtui |
| Found | at the `.git` root only | walking up to `/` |
| Narrows by | bindings, rendered to a filter in the query text, and the existing filter segments an entry references, sent beside the query | existing filter segments, sent beside the query |
| Varies by directory | yes, an entry's `path` | no |
| Selects the environment | never | `environment`, in dtui |
| Unknown keys | of the document: reported, and `set` and `delete` refuse to rewrite; inside an entry: the file is not applied | ignored |

1. **dtctl does not read `.dtui.yaml`.** Its `environment` key picks the context, which is harmless in a read-only viewer and not in a CLI that writes: a cloned file would decide which environment `apply` and `delete` reach, and under which safety level. Its segments would change the rows of a stable command for everyone who already has the file, including a personal one in a home directory. The same segments are available explicitly through `--segment` and `--segments-file`, and a repository that wants them applied by default lists them in an entry of the scope file, where they are validated, vary by directory and are found only at the `.git` root.
2. **dtui is to read the scope file through `pkg/reposcope`,** not through a parser of its own. The lookup rules (the `.git` stop, the regular-file and size check), the validation and the renderer are what make a cloned file safe to honour, and a second implementation would drift in exactly those places. The read path is `Locate`, `Load`, `Resolve`, `Filters` and `dql.InsertFilter`, shown in the package example; none of them writes. An entry's segments are `Status.Entry.Segments`, ids and variable values as validated data, so dtui sends them without parsing a string.
3. **The two narrowings are ANDed and independent.** Segments travel in the request and the scope filter sits in the query text, so a query that has both is narrowed by both (in dtctl today, a scoped query run with `--segment`), and neither replaces, merges with or takes precedence over the other. Each has its own switch. That holds for the segments an entry references as well: they are sent with the workspace file's own, a segment both name is sent once with the workspace file's variables (the nearer, personal file wins, as `--segment` does in dtctl), and the platform's limit of ten per query is dtui's to enforce over the union. Bindings and segments that share no records give no rows, which is the correct answer to the question asked.
4. **The scope file never selects an environment.** `--context`, `DTCTL_CONTEXT` and, in dtui, the workspace file's `environment` decide that; the scope is then looked up under the resulting host, and a host without entries means no scope.
5. **Neither file moves into the other.** A workspace file is hand-written, tolerant of keys it does not know and found from any parent directory; the scope file is written by `set`, refuses to drop what it does not know and belongs to one repository. One file could keep only one of those behaviours.

## Background

The question a developer asks from a checkout is about the code in front of them: what is failing in *this* service, how slow is *this* endpoint. The environment answers in terms of entities (service and process group ids, `service.name`, Kubernetes workloads), and nothing in dtctl connected the two. Every query had to name the entity, and the names in the repository (a Go module, a Helm chart, a Maven artifactId) are rarely the names the environment records.

A repo scope is that connection, written down once and committed: per environment, which entities run this repository's code. Queries made from inside the repository are narrowed to them by default.

`pkg/reposcope` has no view of the invocation. Where the working directory comes from, whether the host grants access to it, and how anything is printed stay in `cmd`; so do flag names, which is why the `set` line discovery proposes is built in `cmd` from a candidate's fields. `store.go` is the only file in the package that touches the host disk; everything else works on values and an `fs.FS`. `pkg/dql` imports nothing from dtctl, so the executor, the hint rules and the scope file share one scanner without depending on one another.

Every Grail field and data object name the package puts into DQL is in `grail.go`. They are fields spans and logs carry today, and the entity ids are classic ids (`SERVICE-…`, `PROCESS_GROUP-…`). `service.name` and `k8s.workload.name` are stable fields in the Dynatrace semantic dictionary; both id fields are deprecated there, `dt.entity.service` in favour of `dt.smartscape.service` and `dt.entity.process_group` in favour of `dt.process_group.id` (Smartscape has no process group entity). See [Evolving the schema](#evolving-the-schema) for what that means for the file.

## The file

### A root file, not `.dtctl/`

The scope file sits at the repository root beside `.dtctl.yaml`, not in a `.dtctl/` directory. `.dtctl/` is ignored in this repository's own `.gitignore` and reads, by convention, as local state; a mapping meant to be committed and reviewed must not live where tooling expects to ignore it.

The walk-up that finds it stops at the first directory holding `.git` (a directory, or the file a worktree or submodule carries), and the file must be in that directory. It never walks past a `.git`, so a parent repository's scope cannot leak into a nested one, and it never accepts a file in a directory without `.git`. This is deliberately not the `.dtctl.yaml` search, which walks to `/`: a scope belongs to one repository. The working directory is resolved through symlinks first. A failed `Getwd` is an error of the command that needed the directory, and of a default-scoped query a silent "off". A parent whose `.git` cannot be inspected ends the walk with "not in a repository"; the local config search differs there too, and keeps walking past a directory it cannot read.

Only a regular file of at most 1 MiB is read. git commits symlinks, so a cloned repository could otherwise point the file at `/dev/zero` or a FIFO and hang every query run inside it.

### Keyed by host

Entries are filed under the environment host (`urls.Host` of the context's environment URL), not the context name. Context names are local to one machine; the file is shared by everyone who clones the repository. It is the same reasoning the config contract applies to token bindings.

### Bindings, never DQL

The file holds structured bindings (namespace/workload pairs, service names, process group ids, service ids), and dtctl renders the filter from them. The alternative, a DQL snippet per entry, is the obvious design and the wrong one: the file arrives with every clone, so it is untrusted input to every query run in the checkout. A snippet could widen a query (`or true`), redirect it, or inject text. Rendered bindings can only narrow: every value is held to its format (`^SERVICE-[0-9A-F]{16}$`, DNS labels for namespaces, DNS subdomains for workloads, printable service names without `"` or `\`) and quoted with `dql.Quote`, and the rendered expression is a disjunction of equality and membership tests on a fixed set of fields.

| Data object | `workloads` | `service-names` | `process-groups` | `services` |
|---|---|---|---|---|
| `spans` | `(k8s.namespace.name == ns and k8s.workload.name == w)`, led by `k8s.cluster.uid == uid and` when the workload binds a cluster | `service.name` | — | `dt.entity.service` |
| `logs` | same | `service.name` | `dt.entity.process_group` | — |

Every output lists the kinds in this order (the workload with its cluster and namespace, the service name, the process group, the service): the two names are stable fields a person recognises, the two ids are deprecated ones, and a reader comparing discover's table, its evidence, a `set` line, `list` and `describe` should not have to re-sort them. The order of the clauses in the rendered filter is left as it was; they are alternatives, so it changes nothing a query returns.

Entity ids always render as `in(field, array(…))`, one id included: logs may carry `dt.entity.process_group` as an array, which `==` would never match. A list of service names renders the same way; one name, and every workload pair, renders as `==`.

### The cluster is part of a workload

A namespace and a workload name identify a workload only within one cluster, so an entry that should select one deployment of several needs the cluster too. It is an optional key of the workload, `cluster-uid`, not a binding of its own:

- **Part of the workload, not an alternative.** Bindings are OR-ed. A cluster beside them would select every record of the cluster; inside the workload it is ANDed with the namespace and the name, which is the only reading that narrows.
- **It narrows its workload only.** A service name or an entity id in the same entry stays an alternative, in every cluster: constraining them too would make the cluster a constraint on the entry, a second meaning for one key, and a `service.name` binding exists exactly for records that carry no Kubernetes fields. An entry meant for one cluster binds the workload alone, which is why discovery's line for a workload in several clusters leaves the shared service name out. `current` and `describe` say what the cluster does not narrow for an entry that mixes the two (`repoScopeClusterNote`).
- **Optional.** An entry without it selects the workload in any cluster, as before, and records that carry no `k8s.cluster.uid` are still reached. With it, only records carrying all three fields are selected.
- **The uid, not the name.** `k8s.cluster.uid` identifies a cluster; `k8s.cluster.name` is chosen when the cluster is connected and can be changed or reused, which would silently move or empty a committed scope. Discovery shows the name beside the uid, because a person tells clusters apart by it, and the file stores only the uid: a stored name would be a second value to keep true and nothing would read it.
- **Validated like every other value.** A lowercase UUID, the form the field carries; anything else is refused before it can reach a query.
- **One flag.** `set --cluster-uid` qualifies every `--workload` of the command, as `--namespace` does, and is refused without them. Workloads in different clusters under one entry are written by hand, the same limit `--namespace` has.
- **A bound field only when bound.** `k8s.cluster.uid` joins the fields a user's own `filter` overrides (`user_filter`) only for an entry that binds a cluster, so a query that filters on the cluster under an entry without one is still scoped.

`cluster-uid` is added under `apiVersion: v1` without the version bump [Evolving the schema](#evolving-the-schema) asks of a key an older dtctl has to cope with. No released dtctl reads the file: repo scope ships first in 0.48.0, with the key. Once a release is out, the rule applies as written.

`set` always replaces the named entry. There is no merge, no `--replace`, and no `--environment`: the root `--context` decides the host.

The file's keys are kebab-case, like the config file. Results printed as JSON, YAML or TOON use camelCase like `sdk/inventory`, an entry inside a result included: a result is not the file, and one spelling per format would give `-o yaml` and `-o yaml --jq .` different keys for the same value. The file is therefore written through types of its own, and the entry type's tags are the result's. And the agent envelope's `context.repo_scope` uses snake_case like every other `context` key.

### Evolving the schema

A typo and a newer dtctl's key look the same to the dtctl that reads them, so where an unknown key sits decides what happens, not what it might mean:

- **A key of the document itself** (beside `apiVersion` and `environments`) is read past, reported as a warning by `current`, `describe` and every scoped query, and refused by `set` and `delete`, which would drop it. It is outside every entry and cannot change what one selects. The exception is a file with such a key and no entry at all: it fails the read (`invalid_file`), because the warning rides on the queries the entries scope and there are none, so nothing would ever say that a misspelled `environments` was not read.
- **A key inside an entry**, on the entry or on one of its workloads or segments, fails the read (`invalid_file`): queries run as typed with the warning, `current` says why, and `--repo-scope <name>` is an error. That is where a constraint is written, and a constraint read past leaves a wider scope behind it: `cluster_uid` for `cluster-uid` binds the workload in every cluster, and `variable` for `variables` sends a segment without its values. A warning beside `applied: true` is not enough for that, because the rows already look scoped. dtctl cannot tell a misspelt constraint from a harmless key, so it reads past none.

A value that fails its format is the same case and gets the same treatment: a `cluster-uid` that is not a UUID, edited in by hand, fails the read rather than being dropped from its workload.

So is a constraint written empty. `path`, a workload's `cluster-uid`, `segments` and a segment's `variables` only narrow, and each means its widest when it is left out: the whole repository, every cluster, no segment, the segment as it stands. Read as "left out", `path: ""` would turn an unfinished line into the whole-repository entry and `cluster-uid: ""` into every cluster, so `""`, `[]` and `{}` under those four keys fail the read with the key and its line (`written` in `decode.go`), as a null does under any key. A list of bindings written empty is refused too. Bindings are alternatives, so one list fewer selects no more, except when it is the last: beside `segments`, `service-names: []` read as left out is an entry of segments alone, which selects everything in the segment. The rule is applied to every list of bindings wherever it stands, which needs no notion of "last". `set` refuses an empty flag value and `Save` leaves an empty key out, so nothing dtctl writes is refused by this.

That makes the rule for `apiVersion: v1`:

- A new document key may be added under v1; an older dtctl warns and applies its entries unchanged. It must not change what an entry selects.
- A new key inside an entry, binding or constraint, is not read by an older dtctl: the file fails to load there and its queries run unscoped, with the `invalid_file` warning naming the key, until dtctl is upgraded. That is the cost of never applying an entry more widely than it is written, and it is paid loudly. A key that an older dtctl must keep working without therefore needs `apiVersion: v2`, which every dtctl refuses by name with the advice to upgrade.
- Changing the format of an existing value needs `apiVersion: v2` as well.

The one exception is written into v1 from its first release: an entry's `annotations`, a map of text to text that dtctl validates in form, bounds in size (64 per entry, a key of at most 253 characters, a value of one line and at most 1024 bytes), keeps on every rewrite and never interprets. Because every key inside an entry fails the read, a dtctl that has shipped can never be taught to skip one, so without a reserved place v1 would have no way to carry anything an older dtctl may ignore. `annotations` is that place, and the promise that makes it safe runs in both directions: an older dtctl reads past whatever a newer one or another tool writes there, and no dtctl, of any version, lets an annotation change what an entry covers or selects. A key that narrows or widens an entry is never an annotation; it is a key of the entry, with the cost described above. `set` has no flag for annotations and keeps the ones the entry it replaces holds.

Entity ids are the change already announced. The file pins classic ids in `dt.entity.service` and `dt.entity.process_group`, and the semantic dictionary deprecates both fields. The migration is `apiVersion: v2`: `services` moves to `dt.smartscape.service` and `process-groups` to `dt.process_group.id`, each with the id format its field carries, and v1 files keep rendering onto the classic fields for as long as the records carry them. The new bindings cannot be added under v1, because they change the format of an existing value. Workload and service-name bindings depend on neither field, which is why discovery proposes them first and offers ids only for a candidate they cannot select, and why the documentation prefers them.

## The Go package

`pkg/reposcope` is one package for two jobs: reading a scope (`Locate`, `Load`, `Resolve`, `Filters`, `Save`) and discovering one (`PlanDiscovery`, `Discover`, the extractors and the ranking). The first is what another program needs and depends on little; the second pulls in `sdk/inventory` and `sdk/api/query`. They ship as one package in the first release because discovery proposes entries with the reader's own validation, and a split made before a second consumer exists would be drawn in the wrong place.

The package's Go API is experimental, like the commands built on it: it may change in any release, and it may be split, with the read path keeping the name. The file format is the contract; the functions are not yet.

## Resolution

For one invocation: the entry named by `--repo-scope`, regardless of its path; otherwise the entry whose `path` covers the working directory, deepest first (by the number of segments, not the length in bytes, which differs between two spellings of one path), compared by whole segments; otherwise the entry with no path. Validation forbids two entries sharing a path, regardless of case. Inside a Gradle build an entry whose path is a module also covers the modules in its closure, as closely as the module holding the working directory; the closure is read from the build files on every resolve with an entry that has a path (`gradleBuildAt`, the discovery walk restricted to Gradle files), a walk of the repository each time, rather than stored in the entry, so the file cannot go stale as the build changes. The build selects an entry only when it was read whole: a build file that did not read, one the walk did not list (each module the settings file names is asked for its build file, so this does not depend on how the walk bounds itself) or the walk's file limit leaves the closure of some deployable unknown, and a library that looks like one deployable's may be shared. The status then carries the reason, and only an entry whose own path covers the directory applies. A literal `project(":a-b")` names the module at that path; a type-safe accessor is matched by its words through an index built once per build. Two entries whose closures share that module tie, and the tie leaves no entry, with a reason naming both, rather than one picked by file order. Paths compare case-insensitively on macOS and Windows; refusing a case-only difference on every OS keeps a committed file valid everywhere or nowhere, instead of resolving by entry order on one and by path on another.

`query` checks cheapest first, and the disk is touched only from the walk-up on: `--no-repo-scope`, or `DTCTL_NO_REPO_SCOPE` when no entry is named; then, without a name, whether the stability policy admits both repo-scope flags on the command; then the context's environment host; then the working directory, which only an invocation with the `HostWorkingDirectory` capability and no session has; then the walk-up and the file. Every "nothing applies" is silent. Every "something resolved but did not apply" (no entry covers this directory, the file does not validate, the rewrite refused) is one warning line and an unchanged query. A broken scope file never fails a query: it is committed, and one bad edit would otherwise break every query run in the repository.

Naming an entry turns each of these into an error before anything is sent, because the caller asked for that entry's rows: a file that does not load is a `validation_error`, an unknown name `not_found`, and every refusal of the rewrite (`not_fetch`, `unsupported_object`, `no_binding`, `subquery`, `unscannable`) a `validation_error` naming the code. `user_filter` is the exception: the user's own filter on a bound field is the answer they asked for, so it runs as typed with the warning.

Resolving a scope sends nothing, and `query` keeps the order of work it had before scopes existed: the storage-scope precheck, the query limits, the flag checks and the resolution of `--segment` come first, each where it always was, and only then does the scope read its entry's segments and print its line. A command line that is refused therefore sends, and prints, what it does without a scope, and with scoping off `query` makes the requests it always made, in the same order (`TestQuery_ScopingOffSendsWhatMainSends` records them).

The stability check exists because scoping is experimental, but only its two flags carry the mark, on commands that are themselves stable; a floor that hides the flags would otherwise leave the rewrite running while refusing its opt-out. So without a name, the policy the floor applied must admit both `--repo-scope` and `--no-repo-scope` on the command, or the query is sent as typed and nothing is printed. A `stability-exceptions` entry for each admits it; one for `--repo-scope` alone admits naming an entry. `DTCTL_NO_REPO_SCOPE` works under any floor.

## The rewrite

dtctl has no DQL parser by design. The rewrite (`dql.InsertFilter`) is a lexical insertion of `| filter (<expr>)` after the leading `fetch` stage, built on the one offset-preserving scanner (`dql.Scan`, which `pkg/dqlhint` uses too), and it refuses whatever it is not sure of, because a wrong rewrite silently returns the wrong data:

- the first stage is not `fetch logs` or `fetch spans` (`not_fetch`, `unsupported_object`)
- the entry binds nothing that data object is filtered by (`no_binding`)
- a `filter`/`filterOut` stage already compares a bound field (`user_filter`): the user's own filter wins. The same field in `summarize by:`, `fields`, a comment or a string is not an override, and neither is one inside square brackets of the filter stage, where it is a subquery's field or an index (`filter x in [data record(...) | fields k8s.workload.name]`, `filter tags[k8s.workload.name] == "x"`)
- a scoped data object is fetched again at bracket depth > 0 (`subquery`): scoping only the outer fetch would report "applied" over environment-wide rows
- not refused, and so a stated limit: a subquery on a data object the scope does not filter (`append [fetch bizevents]`, `lookup [fetch dt.entity.service]`) and literal rows (`append [data record(...)]`). Their rows are not narrowed, and the outcome is still `applied` for the leading fetch, which is what the line and `data_object` name. Refusing them would refuse every entity lookup, the most ordinary subquery there is. Segments have the same edge on the platform's side: its documentation says subqueries in `join`, `lookup` and `in` run outside the query's segments
- an unterminated literal or comment, unbalanced brackets, a single quote, or a `#` outside a literal and a comment (`unscannable`). The scanner masks with `#`, so one typed as code would read as a comment and hide what follows it. DQL comments are `//` and `/* */`, which is what every other DQL reader in dtctl assumes; that Grail rejects a bare `#` has not been verified against an environment
- a triple-quoted string whose three closing quotes are followed by a fourth (`"""a""""`, also `unscannable`). Such a run ends the string at its first three quotes or at its last three, and the two readings disagree on whether what follows is code. Dynatrace's published DQL formatter closes at the last three; which one Grail does has not been verified against an environment, so the scan vouches for neither. The cost is a string that ends in a quote, which is refused where it used to be scoped

Grail reads command and data object names without regard to case, and field names with it: on an environment `FETCH Spans`, `| FILTER` and `append [Fetch Spans]` ran like their lower-case spellings, while `K8S.Namespace.Name` matched nothing. The rewrite follows that. `fetch Spans` is scoped as `spans`; a nested `Fetch Spans` is the subquery it is, which matters more, since missing it would report "applied" over environment-wide rows; and a bound field counts as the user's own filter only as written.

Two invariants are tested on every row of the rewrite table: when not applied, the output equals the input byte for byte; when applied, removing the inserted range gives back the input. `FuzzInsertFilter` (`pkg/dql/fuzz_test.go`) holds the rewrite to them for any text, valid UTF-8 or not, and to three more: the inserted range is the stage `| filter (<expr>)` at the first depth-0 pipe, or at the end of the text; the result scans with that stage second and with every byte of the input reading as it did before, as code or as masked text and at the same bracket depth; and the rewrite is idempotent in the one sense it can be, that applied to its own result it inserts nothing, because the query now filters a bound field itself (`user_filter`).

A scoped query that returns nothing is diagnosed on the text the user typed, not the one sent, so the empty-result diagnosis never blames a field the scope inserted. Its sample of the data object is taken inside the scope, with the inserted stage and the segments that were sent: a field can be absent from the environment's records at large and present on every record of the service, and the other way round. A binding that matches nothing therefore yields no sample and no field diagnosis, which is right, and the suggestion to compare with `--no-repo-scope` comes first either way.

**What counts as nothing.** Zero rows, and one more shape: a query whose last stage is an ungrouped `summarize` returns one row whatever it was given, so `fetch logs | summarize c = count()` under a scope that matches no record answers `c = 0` and looked like a result. `dql.UngroupedCount` finds, lexically, the column such a stage counts every record in (`count()`, named or not, as a whole aggregation), and a 0 there gets the zero-rows hint. Nothing else is inferred: `countIf`, `sum` and the like can be zero over plenty of records, and Grail's metadata reports the records scanned, not the ones a filter let through, so it cannot tell either. `wait query` gets no hint per attempt, where zero rows are the condition not met yet, but its outcome names the scope once: when the wait ends unmet, and when a condition is satisfied by zero records (`--for none`), which is exactly what a scope that matches nothing produces at once.

**Scope and scan cost.** The inserted filter narrows the rows and, as an equality filter right after `fetch`, helps the scan, but it cannot by itself keep a wide timeframe under the scan limit. `sdk/inventory/sampling.go` records the measurement: a scoped, unsampled 15-minute count of logs still scanned 341 GB on a large environment, against 500 GB for the capped unscoped read. Nothing honest can be inserted to change that: a timeframe changes the question, `samplingRatio` makes every scoped result approximate, and a scan cap is not scoping. So the rewrite sends what it always sent, and says so before sending: when neither the fetch stage (a `scanLimitGBytes` above 0, a `samplingRatio` above 1, or a value the scan cannot read as a number; `Rewrite.ScanBounded`) nor the resolved scan limit or sampling ratio bounds the scan, the scope line ends with a clause that only the environment's default cap applies. A limit of `-1` (`Rewrite.ScanLimitLifted`, or the flag) removes that cap too, and the clause then says that no scan limit applies. The clause is advice given before the run. A scoped query the cap stopped gets one line after the run, worded to agree with the executor's "filter early with ==" hint, which lists the other levers, and it gets that line whether or not the clause was printed: what was advised is not what was observed. `decorate` carries one scan suggestion, the observed cap when there is one and the clause otherwise. `wait query` says either once; `verify query` sends no query and has no clause.

## Segments an entry references

An entry may list existing filter segments, each with the values of its variables. A query run under the entry sends them as if `--segment` had been typed:

```yaml
- name: checkout
  workloads:
    - namespace: payments
      name: checkout
  segments:
    - id: Ab3dEf9hIjk
      variables:
        environment: [production]
```

- **By id, never by name.** `--segment` resolves a name with a list call and takes the first match; a committed file must not change meaning when someone renames a segment or creates a second one of that name. `variables` is a map from name to values, so a variable cannot be given twice, where `--segments-file` takes the API's list.
- **Validated like every binding.** An id is letters, digits, `-` and `_`; a variable name is a DQL identifier that may hold dots; values are printable text of bounded length without `,`, `&` or `=`, so that the `--segment` spelling every notice prints reads back as the reference it came from; an entry holds at most ten segments, the platform's limit per query, and names none twice. Ids and values travel in the request body as JSON, never in the query text, so there is nothing to quote, but nothing unchecked leaves the machine either.
- **ANDed with the bindings.** The bindings stay alternatives among themselves; the filter they render and every segment must all hold. Like `cluster-uid` it is added under v1 because no released dtctl reads the file (see [Evolving the schema](#evolving-the-schema)).
- **An entry may hold only segments.** It then inserts no filter and applies wherever segments do, `timeseries` and events included, which no binding reaches today.
- **Which commands.** `query` sends them, and `wait query` when an entry is named. `verify query`, which is scoped only under a name too, does not: verification takes the query text and nothing else, so it says the entry's segments were neither read nor sent, and that `query` sends them. It does not read them to predict what `query` will do: the answer would cost a request per segment on a command that otherwise sends one. An entry that holds only segments leaves `verify query` nothing to apply, and the scope then reports `applied: false` with the code `segments_not_sent`, never `applied`. `exec dql` is never scoped. The Live Debugger commands ignore them, because a workspace is filtered by labels, not by segments: an entry that holds only segments renders no filter set, with that reason, and the user guide says it where breakpoints are described.
- **With the user's own.** `--segment`, `--segments-file` and the entry's are sent together. A segment the user names that the entry also lists is sent once, with the user's variables, and a line says so: what is typed wins over what is committed, as the user's own `filter` on a bound field does. The envelope then reports `applied: false` with `user_segment`, as it does for that filter: the variables sent for the segment are not the committed ones, and a scope reported as applied must not be wider than the file says. `filter` and `segments` still list what of the entry went out. From there it is the user's segment. The command line is read before the scope says anything, so the scope line and `context.repo_scope.segments` list what the entry itself sent, the entry's copy is not read, and an entry that holds only segments, all of them given by the user, reports `applied: false` with code `user_segment`. `--segment-var` binds variables of a segment given with `--segment`; aimed at one only the entry references, it fails before any request and names the `--segment` spelling that overrides it. More than ten in total is an error before anything is sent, naming `--no-repo-scope`; dropping some silently would change the rows.
- **Switches.** `--no-repo-scope`, `DTCTL_NO_REPO_SCOPE` and a stability floor that hides the flags turn the entry off whole, segments included. There is no switch for the segments alone.
- **What is shown.** The scope line on stderr lists them (`segments Ab3dEf9hIjk?environment=production`), in the spelling `--segment` takes. `context.repo_scope.segments` carries them as data. `applied` is true when everything the entry holds went out: its filter, and its segments when it has any. An entry without bindings is applied by its segments alone, and one whose filter was refused is not applied although its segments are sent (see the next point). `filter` is empty when none was inserted. `describe` and `list` print them, and `describe` words its filter section by them: an entry that holds only segments is not one that "binds nothing", and an object its bindings do not filter is still sent with its segments.
- **The filter and the segments fail apart.** When the rewrite cannot insert the filter (`not_fetch`, `user_filter` and the rest) the entry's segments are still sent, and the line says which half applied. The envelope does not call that applied: a scope reported as applied is never wider than the file says, so the scope carries `applied: false` with the refusal's code and lists the segments that went out. What follows a changed request (the zero-records line, the suggestion to run unscoped, the error wrapping) keys on the request having changed (`changedRequest`), not on `applied`. Under `--repo-scope <name>` a refused rewrite stays the error it was when the entry has bindings: the caller asked for that entry's rows.
- **A segment that cannot be used fails the whole scope, loudly.** The platform fails a query that names a segment it cannot find (`FILTER_SEGMENT_NOT_FOUND`), so one deleted segment would break every query in the repository. Before sending, dtctl reads each of the entry's segments once (`GET` by id, at most ten, once per invocation however often `wait query` polls). If one is missing or unreadable (deleted, not shared with this user, or a token without `storage:filter-segments:read`), the query runs exactly as typed, without the filter either, with a warning naming the segment and code `segment_unavailable`. Half a scope would return rows that look scoped and are not. Under `--repo-scope <name>` it is an error.
- **Only "not there" degrades.** The unscoped run is for a segment that is missing (404) or not this caller's to read (403): states that stay as they are until someone edits the entry or the segment. Every other failed read, a server error, a rate limit or a timeout after the client's retries, is an error and nothing is sent. It says nothing about the segment, and an unscoped run with exit 0 on a fault that passes a moment later would hand a script environment-wide rows for a query that is scoped on the next run.
- **`wait query` scopes only under a name.** `query` says what it did on every run, next to its rows and in the envelope. A wait is consumed by its exit code, in scripts and CI where nobody reads stderr, and its outcome (met, or not) reads the same whether a scope narrowed it, was dropped, or never applied. So `wait query` has no default scope and no `--no-repo-scope`: it applies an entry when `--repo-scope <name>` asks for it, and there everything that cannot be applied is already an error, a segment that is gone included. Without the name it is the command it was before repo scopes, request for request, plus one line on stderr when the covering entry would have changed the request (`repoScopeHint`), which `--quiet`, `DTCTL_NO_REPO_SCOPE` and a stability floor that hides the flag all silence.
- **`verify query` scopes only under a name, for the same reason.** Everything it produces is consumed by a program: the exit code gates a commit or a CI job over committed `.dql` files, `--canonical` is written back to the file it was read from, and structured diagnostics carry positions in the text. Scoped by default, `--canonical` returned the canonical form of a query with a filter the author never wrote, which a formatting script would then commit, and the inserted stage adds nothing to a syntax check. It also never verified what `query` sends, since it drops the entry's segments. So it follows `wait query`: `--repo-scope <name>` verifies the scoped text, the entry's segments still unsent and said to be; no `--no-repo-scope`; and without the name the request and stdout are what they are outside a repository, plus the one stderr line when the covering entry would have inserted its filter (it has no `--quiet`; `DTCTL_NO_REPO_SCOPE` and the stability floor silence it). An entry that holds only segments offers `verify query` nothing and gets no line.
- **Live mode never refreshes unscoped.** `query --live` re-runs the query for as long as it is open, and its one warning is on a screen the first redraw clears, so a live run whose scope was dropped over a segment does not start (`requireSegments`). What live mode still lacks is the scope in its redrawn header (see the follow-ups).
- **The read is the smallest one.** It asks for the segment without `add-fields`: the check needs to know the segment is readable, not what it includes. The reads run one after another. In parallel, ten of them arrive as a burst against the same rate limit, and a rate-limited read is an error; the time saved is under two seconds on an entry with the maximum of ten.
- **What the check cannot see.** dtctl does not check a segment's variables before sending; the platform does, and fails the query in two ways. A required variable the entry gives no value is `FILTER_SEGMENT_REQUIRES_VARIABLE`. A variable the query's data cannot supply is `MISSING_FILTER_SEGMENT_VARIABLE`, and that one reaches queries the entry has nothing to do with: a segment written for logs fails an entity query run in the same repository. Checking first would need each segment's definition and a model of which data object supplies what, so dtctl rewords the failure instead. The executor's own text advises `-S "<id>?var=value"`, which is wrong for a segment the user never typed, so for a segment the entry sent the error names the entry and the file as the source and both ways out, correcting the entry or `--no-repo-scope`, in the human text and in agent mode under the code `repo_scope_segment_variable` (`ScopedQueryError.segmentVariable`). A segment the user gave keeps the executor's text. `wait query` treats both as what they are, refusals no retry changes: the waiter ends on the first (`isPermanentQueryError` knows `exec.SegmentVariableError` by its type, since the executor's message for it does not carry the 400), and prints the error as the scope words it, with the text sent (`WaitConfig.ExplainError`). A variable the segment does not declare is ignored by the platform, and a value it does not know selects nothing, which the zero-records line covers.
- **Cost.** One small read per referenced segment per invocation, and nothing for an entry without segments. Probing with a query was rejected: a query over `data record()` does not validate its segments, and a real one would scan.

## Live Debugger

A Live Debugger workspace is filtered by labels its processes carry, under the same names as the record fields an entry binds, so an entry can set workspace filters as well as narrow queries. `reposcope.LiveDebuggerFilters` renders it into the type `--filters` parses to and `livedebugger.BuildFilterSets` takes, `map[string][]string`. `Resolve` renders once into `Status.LiveDebuggerFilters`, the one rendering `repo-scope describe`, `-o json` and both breakpoint paths read (through `Status.LiveDebuggerFilterSets`, which carries the reason when there is none).

`--repo-scope <name>` is a filter source like `--filters`, resolved before any network call through `resolveRepoScope`, so its failures are the same errors as on `query`; both sources go through `applyWorkspaceFilters`, the one place the breakpoint commands change workspace filters.

`create` sets no filters from an entry nobody named. An earlier version did: a workspace without filters took the covering entry's one namespace-and-workload set. It was withdrawn before release, because a workspace's filters decide where every breakpoint in it can hit and what a workspace does with the labels an entry renders is only partly verified (see the open questions below): a default built on that would fail silently, as a breakpoint that is created and never hits. So a create that names no filters only reads the entry covering the working directory (`coveringBreakpointEntry`, from the resolution that named the workspace) and says it exists: in the error when the workspace has no filters, and otherwise in one line, also a `context.suggestions` entry, when the workspace's filters are not the entry's. `DTCTL_NO_REPO_SCOPE` and a stability floor that hides `--repo-scope` silence both, and `create breakpoint` has no `--no-repo-scope`. The path that applies an entry is the named one and is unchanged; the default may return once the verification procedure below has been run (see the follow-ups). The dry run sends nothing, and so says that the workspace must have filters instead of checking: the only request that reads a workspace, `getOrCreateUserWorkspaceV2`, also creates it, and a command on `dryRunCommands` promises a preview that writes nothing. It never newly requires config.

The workspace is named `<repo>/<entry>` (`resolveBreakpointWorkspace`), the repository taken from the origin remote so a clone's directory name does not matter: the entry `--repo-scope` names, wherever the command runs, or else the entry covering the working directory. A directory of the checkout no entry covers, or two tie on, gets `<repo>`. The repository names a workspace only where the scope file has entries for the context's environment, the rule `resolveRepoScope` applies to queries: everywhere else the working directory's base name is used, as before repo scopes existed, so a file written for another environment moves nobody's breakpoints. Only a plain name is taken from the remote (letters, digits, `.`, `_`, `-`); a remote that ends in anything else, like a checkout without an origin, falls back to the checkout directory's base name, because the name is sent and printed. The base name alone changed with every `cd`, collided across repositories (`src`) and did not compose with the entry; the repository alone would make two entries fight over one workspace's filters. That is also why a named entry names the workspace: run from a library `webproxy` and `admin` share, `--repo-scope admin` would otherwise re-scope the breakpoints `--repo-scope webproxy` had put in `<repo>`. Naming ignores `DTCTL_NO_REPO_SCOPE` and the stability floor, because naming is not scoping.

A scope file that is there and does not load names nothing, and no command guesses. A query can run unscoped under a broken file, because the worst outcome is rows the user did not narrow; a breakpoint command would work in a different workspace, where `delete breakpoint --all` deletes and a filter change re-scopes breakpoints the user never meant. So `create`, `update` and `delete breakpoint`, dry runs included, fail with the file's error (`breakpointWorkspace.requireScopeFile`), and the read commands read the directory-named workspace with a warning that says so (`readWarnings`). An existing user's directory-named workspace is not migrated; the Live Debugger guide says how it stays reachable.

**Safety.** A filter write is checked as an update whichever command makes it, so `create breakpoint --filters` and `--repo-scope` need the update level beside the create level. That is a behaviour change from 0.47 and earlier, where create's filter write was checked as a create only: a `readwrite-mine` context, which cannot tell whose a workspace's breakpoints are, no longer sets filters through `create` that it was always refused through `update`. It may be relaxed for both commands together once a workspace is shown to be private to its user.

**A create that fails after its filter write** is not rolled back. Setting the filters and creating the breakpoint are two requests; undoing the first is a third that can fail too and re-scopes the workspace again, and a workspace that had no filters cannot be returned to that state at all (follow-up 9). `filtersChangedError` says instead what the filters were and are, in which workspace, and which commands show them, restore them where one `--filters` value can or the entry the workspace is named after renders exactly them, and retry. Each of those lines, and the hint of a create whose workspace does not hold the covering entry's filters, carries `--context` (and `--config` when the flag or `DTCTL_CONFIG` chose the config file) and is quoted for a shell: a repository names the same workspace in every environment, so a line pasted under another current context would otherwise write there.

**Verified against an environment.** Namespace with workload, and process group, are honoured as labels; the labels of a set are ANDed and several sets ORed. `dt.entity.service` selects nothing, so service ids are left out of the rendering, and an entry that binds only those renders none, with a reason.

**Open questions: not verified against an environment.** No write of this integration has been tried against a live environment. Each item below is said in the Live Debugger guide ([What is not verified](../LIVE_DEBUGGER.md#what-is-not-verified)), and the ones a user is about to rely on are said by the command, on stderr and in `context.warnings`, before it asks or writes.

1. Whether a workspace name may contain `/`, as `<repo>/<entry>` does. Said by every command that changes something in a workspace of a linked checkout (`breakpointWorkspace.changeNotes`).
2. Whether a workspace is private to the user who created it. Every clone of a repository names the same workspace, so if it is shared, one user's filter change or `delete breakpoint --all` reaches another's breakpoints. Said in the same line where the origin remote named the workspace (a name taken from the checkout directory is promised to no other clone, and the line says that instead); it is also why a `readwrite-mine` context is refused every filter write and delete.
3. Whether `service.name` is honoured as a workspace label. Said whenever filters are set from an entry that binds a service name (`entryFilterNotes`).
4. Whether `k8s.cluster.uid` is honoured. It is not sent, and the commands say that the filters are wider than the entry.
5. That a breakpoint under a filter set the workspace does not honour is created without complaint and never hits. This is the failure mode of items 3 and 4, and the reason nothing is set from an entry nobody named; the `service.name` line names `dtctl describe breakpoint <id> --repo-scope <name>` as the check, with the entry, since the filters were set in that entry's workspace.
6. Whether a new workspace reports its filters as `[]`, `null` or not at all, its rules as `[]` or `null`, and what `updateWorkspaceV2` answers. The decoders read all of these as "no filters", "no breakpoints" and "applied" (follow-up 32).
7. Whether a workspace created through dtctl ever has `sources`, which every filter update sends as `[]` (follow-up 33).

**Verification procedure.** To run by hand in a non-production environment, in a clone that has an origin remote and a scope file with `<entry-with-workload>` covering the checkout root and `<entry-with-service-name-only>` covering a subdirectory, with a `readwrite-all` context. Each step names the open question it settles, and every step that reads looks in the workspace the step before it changed. Three workspaces are used: `<repo>/<entry-with-workload>` (W1), `<repo>/<entry-with-service-name-only>` (W2), and the directory-named one of step 7.

1. **First, because the cost of a shared name depends on it (question 2, follow-up 43):** `dtctl create breakpoint <File>:<line> --repo-scope <entry-with-workload> -v` at the checkout root, then ask a colleague, with their own user, to run `dtctl get breakpoints -v` in their clone of the same repository against the same environment. Do they see your breakpoint, and is `creatorEmail` yours or theirs? If they do, a workspace is shared, and every filter change and `delete breakpoint --all` in a linked checkout reaches every colleague's breakpoints.
2. From the `-v` output of step 1: the create succeeds with `/` in the workspace name (question 1); compare the `name` the `getOrCreateUserWorkspaceV2` response carries with the project path sent, since a name the environment rewrites is how two `<repo>/<entry>` workspaces would collide; note whether the `updateWorkspaceV2` response carries the id and the filter sets sent (question 6).
3. `dtctl get breakpoints -v` in a fresh directory outside every checkout: is `filterSets` `[]`, `null` or absent, is `rules` `[]` or `null`, what does `sources` hold (questions 6 and 7). Then look for a workspace of that directory's name in the Live Debugger UI: if it is there, a read created it (follow-up 42).
4. `dtctl describe breakpoint <id>` at the checkout root, which is W1: the workload's processes are listed as reached, and a hit produces a row in `dtctl get snapshots <id>`.
5. Still at the checkout root, in W1, which holds the breakpoint of step 1: `dtctl update breakpoint --filters k8s.cluster.uid:<uid>,k8s.namespace.name:<ns>,k8s.workload.name:<wl>`, then `dtctl describe breakpoint <id>`: reached processes or none (question 4, and with it whether the cluster can be sent). Restore with `dtctl update breakpoint --repo-scope <entry-with-workload>`.
6. `dtctl create breakpoint <File>:<line> --repo-scope <entry-with-service-name-only>`, which works in W2 and prints the id, then `dtctl describe breakpoint <id> --repo-scope <entry-with-service-name-only>`: does `service.name` reach the processes of that service, none, or every process (questions 3 and 5)? "Every process" would mean an unknown label is ignored rather than matching nothing, and `service.name` must then not be sent.
7. Before the scope file is committed, or with it moved aside: `dtctl create breakpoint <File>:<line> --filters <key>:<value>` in a subdirectory `<dir>` of the clone, which works in the workspace `<dir>`. With the file back, from a directory called `<dir>` outside every checkout, with `--context` naming the same context: `dtctl get breakpoints` still lists that breakpoint.
8. `dtctl delete breakpoint --all` in each workspace used: at the checkout root (W1), with `--repo-scope <entry-with-service-name-only>` (W2), and in the outside directories of steps 3 and 7; confirm with `get breakpoints` in each of the four that it is empty.

**The cluster is not sent.** A workload's cluster is left out of its filter set, so a workspace set from an entry that binds one is wider than the entry: it includes the same namespace and workload in other clusters. Nothing shows a workspace honouring `k8s.cluster.uid`: the Live Debugger code and tests here never send it, and it has not been tried against an environment. Sending it unverified was the first choice and was withdrawn. Discovery proposes `--cluster-uid` whenever records carry one, so the ordinary path from `discover` to `set` to `create breakpoint` would have set a label of unknown effect, and a set whose label a workspace does not know selects nothing: a breakpoint that is created without complaint and never hits. Here the principle that a scope is never wider than the file cannot be met by failing, because refusing every breakpoint for an entry that binds a cluster takes `--repo-scope` away from exactly the entries discovery writes. So the commands say what they did instead: every path that sets filters from such an entry, its dry run included, says that the workspace is not narrowed by cluster, and `describe` prints it under the filter sets. It is one of the lines `entryFilterNotes` renders, with the service ids and filter segments that are left out and the unverified `service.name` that is sent; `sayBreakpointWarnings` prints them before the confirmation and the write and carries them into `context.warnings`, so an agent reads what a person saw. Sending the label needs one breakpoint verified to hit with it (follow-up 7).

## Discovery

### Record aggregates first

Discovery answers "which entities run this code" from records, not from the entity model. Its two primary queries aggregate the last 24 hours of spans and logs whose `k8s.workload.name` or `service.name` is one of the repository's names, or whose workload name holds one as a run of segments, one row per cluster, namespace, workload and service name, with each entity id field counted (`countDistinct`) and collected up to 51 (`collectDistinct(…, maxLength:51)`), one more than the 50 a row is read for. Grouping by identity rather than by id matters on a large environment, where one workload can run as a couple of hundred service ids: grouped by id, that one workload filled the 200-row page by itself. The list is what a binding can use, and the 51st id is how a cut list shows: `countDistinct` is an estimate in DQL, and for a field that is itself an array it counts arrays, so comparing it with the list cannot tell a cut list from a whole one. A whole list is its own count. A candidate with a cut list is capped (`servicesCapped`), its count is the estimate, at least 51, its per-kind verdict is tallied from the count, and no id binding is proposed for it. That proves the fields exist on the records the scope will later filter, fills in the namespace, and returns ids in exactly the form the renderer compares. The entity tables (`dt.entity.service`, `dt.entity.process_group`) are searched by name only when the records find nothing, and are reported with a note on environments that do not offer them.

The record queries find logs by workload and service name, and logs need not carry either: on one environment a workload's spans carried `k8s.workload.name` while its logs carried the namespace and `dt.entity.process_group` only, so the proposed workload binding returned every span and none of about 5000 logs, and the report said nothing. Discovery therefore looks at each candidate with spans and no logs (`checkLogs`). When both record queries read the whole window, the candidate lists all of its process groups, and no candidate of another workload carries one of them (`ownsProcessGroups`), one more query counts the logs carrying those ids, with the expression a process-group binding renders, so it counts what the entry would reach. A candidate it finds logs for carries the count (`logsByProcessGroup`) and its line binds the process group; every other such candidate gets a note saying its logs were not found, by the names alone or by the process group too. The lookup is skipped past 50 ids, and its failure is a note, never a partial report: it can miss a binding, not a candidate. A capped or sampled logs query has not shown the logs to be absent, so nothing is checked or said after one.

Names are read per unit: the nearest directory at or above the working directory (or `--path`) that holds a build file (`go.mod`, `package.json`, `pom.xml`, `build.gradle(.kts)`, `settings.gradle(.kts)`, `pyproject.toml`, `*.csproj`) or a Dockerfile; the repository root otherwise. Kubernetes manifests and Helm charts contribute names to the unit named like them, or the nearest one above them, but do not make units. Every Maven module is its own unit. A Gradle build is not (`extract_gradle.go`): most of its modules are libraries of what it deploys, so a per-module unit attributed a deployable's chart to the deployable alone, left the libraries covered by nothing, and proposed `--path <module>` from inside each. A module is deployed when it holds a Dockerfile or a Helm chart or workload manifest holds or names it, unless it is named like a test. With at most one, the build is one unit at its settings file and no module's directory name is sent; with several, each deployable is a unit whose proposed entry covers its module, and resolution adds its transitive module dependencies (`include` lists, `project(":x")`, `project(path: ":x")` and `projects.x` references outside test configurations, read by regexp with no DSL model), and a library several deployables share, like the settings directory, is discovered for each of them in turn (`Plan.SharedBy` names them; the command plans one discovery per deployable and prints one report each). `projectDir` remaps are not read. Treating Maven builds the same way is left until field data asks for it.

The queries are fixed, eleven planned and at most ten sent (the entity searches and the process-group lookup exclude each other), capped in their own text (`scanLimitGBytes:5`, `limit 200`), and bounded by a 60-second deadline per unit (a directory several Gradle deployables share is discovered once for each, every run with its own bound). The filter helps the scan but cannot keep a day of a busy environment's spans or logs under 5 GB (inventory measured a scoped 15-minute log count at 341 GB unsampled), and a capped scan covers an unknown part of the window, so it cannot support a `match`. Sampling is the one lever that reduces the scan itself, so when the cap stops a record query its rows are set aside (their counts are not comparable with a sample's, but an identity they name that the answering rung does not return stays a candidate without a count, and makes the report partial) and the query is retried at `samplingRatio`: 1-in-100000 over 1h, 1-in-100000 over 24h, 1-in-1000 over 24h, coarsest first. Unlike inventory's ladder, which descends until the sample is thick enough to date a record, the walk stops at the first rung that finds a candidate, because discovery needs identities, not a precise count; the common case pays one near-free query. Before each rung the previous rung's scanned bytes are scaled by the step (×24, ×100) and a rung predicted to exceed the cap is skipped (`predicted_cap`); a rung Grail does not sample ends the walk (`sampling_refused`) and the capped rows stand. Grail omits the sampled flag from a result that scanned no record, so a rung is refused only when it came back unsampled having read something; one that read nothing is empty, and the next rung runs. The floor every note states is inventory's (`SampledMissBound`), computed from the requested ratio, since Grail only ever samples more finely than asked. The runner hands discovery every truncating notification of a response (`RunResult.Truncations`), not only the first: a scan cap decides wherever it stands in the list, and a typed `RESULT_LIMIT_RECORDS` or `RESULT_LIMIT_BYTES` is a cut page however short the page. A result limit recognised by its message alone is a cut page too, since some deployments report one in no other way, with one exception: on a query that collects ids, when a row of the page holds an id array longer than a binding takes. Grail may word a collected id array that reached its `maxLength` that way, and that row is then what the message is about. Which notification Grail sends for a cut `collectDistinct`, and whether it returns the array at 51 elements, has not been observed on an environment; if it clips shorter, such a report is partial, which is the safe side. An id column is bounded at 50 ids after flattening, not at 50 arrays: a log field that is itself an array can hold any number in one element (`collectDistinct(..., expand:true)` would move that bound into the query, and is not used because it is unverified). A sampled retry that is cut short or comes back unsampled is no answer, but the identities its rows name are kept like the capped scan's, as candidates without a count (`cappedScan`). The entity-name searches add the name's length as a field and sort on it, because DQL documents `sort` over fields; sorting on `stringLength(entity.name)` directly is not documented. There are no budget flags. None of this has run against an environment: the query texts follow the DQL documentation and are tested against recorded answers. Not verified without one are that the texts run as written (`collectDistinct` without `expand` on `dt.entity.process_group` where that field is an array, and `summarize ... by:{dt.entity.process_group}` on it in the process-group lookup, which a reviewer expects Grail to refuse and nobody has tried), which fields a deployment's spans and logs carry, which notification types Grail sends, and what each query scans, the search inside workload names included. A read of the whole window is a read of what the token can see: records in a bucket it has no permission for are absent without a word. Discovery is read-only, so like `inventory` it sets up a client without a safety check, and it runs in a `readonly` context. `dqlScopePrecheck` runs on the two record queries before the first is sent, so an OAuth token that provably cannot read spans or logs is refused up front rather than after half a report. The entity fallbacks are checked only when they are about to run, and a token that cannot read them gets an `auth` note instead: they are a fallback, and discovery answers without them.

### The cluster is part of a candidate

The record queries group by `k8s.cluster.uid` as well, so one namespace and workload name in two clusters is two rows and two candidates, never one merged row whose counts and ids belong to neither. `clusterName = takeAny(k8s.cluster.name)` rides along for the reader; it is aggregated rather than grouped by, so a renamed cluster stays one row.

- **The `set` line binds the cluster the candidate's records name.** The line has to save exactly the candidate shown, and without `--cluster-uid` it would save every cluster's workload of that name.
- **Two clusters are `ambiguous`.** Each candidate has its own line, and `Candidate.WorkloadShared` marks them. A service that runs in both is a legitimate answer no line gives, since `--cluster-uid` takes one cluster, so a note names the two ways to bind it: a line without `--cluster-uid`, or one workload per cluster written in the file.
- **No cluster beside a cluster.** A row whose records carry no `k8s.cluster.uid`, while another row has the same namespace and workload in a cluster, gets no workload binding and a note: its only honest line would also select the other candidate.
- **A sampled candidate keeps its cluster.** Ids are withheld from a sampled or capped candidate because discovery may have listed only some of them. The cluster is a key the rows were grouped by, so it is whole or absent; what a sample can miss is another candidate, in another cluster or not, and the floor note already says that.
- **A cluster on some records only.** Spans may carry `k8s.cluster.uid` while the logs of the same namespace and workload carry none. The row without a cluster then joins the candidate in the cluster (`foldClusterless`), provided that namespace and workload have exactly one candidate in a cluster and the row carries its service name or none: anything less certain stays a candidate of its own, under the rule above. The candidate lists the data objects that carry no cluster (`Candidate.WithoutCluster`), and its `set` line leaves `--cluster-uid` out, with a note. A line with the cluster would save an entry that returns every span and no log, which reads like a quiet service; without it the entry reaches both, and no other candidate runs that workload for the wider binding to select. A process-group binding beside the cluster was the alternative, and was rejected: it leans on a deprecated id that changes with redeploys to keep a constraint only half the records can satisfy.
- **A value that is not a UUID** keeps its rows apart and is not proposed, since `set` would refuse it. The candidate carries the value (`Candidate.ClusterRefused`), so its evidence and the note about a missing line say what the records hold rather than that they name no cluster.
- **The process-group lookup** treats the same workload name in another cluster as another workload, so it is skipped when both carry the process group.

### Workload names with a prefix

A workload is often deployed as `<org>-<env>-<name>` while the repository says `<name>`, and comparing names whole found nothing. The record queries now also keep a row when a sent name is a whole run of the workload name's segments, the parts between `-` and `.`, the characters a workload name can hold besides letters and digits.

- **In the same query.** The first filter adds `contains(k8s.workload.name, …)`; after the aggregation a second filter keeps the rows that match exactly or hold the name between delimiters, tested on the name with `.` folded to `-` and a `-` at each end. The plan stays at eleven queries and the row limit applies after the second filter. The clause is not free, though. Where no record's workload name holds a sent name, the query scans what it scanned without the clause. Where records do, they are kept by the first filter and read for the aggregation, and on an environment with many such workloads a run scanned many times the bytes of the same query without the clause. That cost falls on the runs the clause serves, it counts against the same 5 GB cap, and a capped query is retried sampled like any other. A separate query was the alternative: it would have added a scan to every run, including those where nothing holds the name.
- **Segments, not substrings.** `checkout` is in `acme-prod-checkout` and not in `checkouts` or `precheckout`. The entity-name fallback already ranks this way (`containsSegment`); a substring tier for records would propose unrelated workloads on a busy environment.
- **At least five letters and digits** (`minSegmentRunes`). Three is enough to send a name for an exact comparison, but `api`, `web` or `cart` is a segment of workloads all over a cluster; such a name still matches whole. Five is a judgement, not a measurement.
- **Below exact, in the query too.** The aggregated rows sort by whether the workload or service name is a sent value (`nameTier`), then by records, before `limit 200`. Sorted by records alone, a busy environment's workloads that merely hold the name could fill the page and cut off the one named exactly, and the report would be partial without its best candidate.
- **Below exact, and never a match alone.** A `segment` candidate ranks under any exact one whatever its volume, and a sole one is `ambiguous`: the repository does not say which prefix is its own, so a person confirms it. The evidence line names the workload, the value it holds and where the value was read.
- **Workloads only.** `service.name` is free text with no delimiter convention to lean on, and is compared whole.
- **Known miss.** The first filter looks for a multi-word name joined by `-` and by `.`; a workload that mixes the two inside the repository's name is not found.

### What leaves the machine

Only names derived from the repository and the user's `--term` values, in their match variants; namespaces are evidence, never sent. The process-group lookup sends ids, but they are the environment's own answer to the spans query, not something read from the machine; the plan shows that query with a placeholder in their place. Generic words are dropped, as are a directory's layout name (`layoutWords`) and a Dockerfile's launchers, and a `--term` is held to what a name read from the repository is: `PlanDiscovery` refuses one made of other characters, shorter than three letters or digits, or generic, so no flag sends what the readers would not. A name is looked for inside workload names only in the one spelling a workload name can hold (lowercase words joined with `-`, and the same with `.`), which is always a sent value, so `sent` is every literal the queries carry.

Test content is not a source of names: a `kind: Deployment` under `test/fixtures/` or a `Dockerfile.test` describes what a test deploys, not what runs, and a candidate found under `test-platform-service-a` would link the repository to a test double. One word set in `tokens.go` (`testWords`) drives three rules, each extending it by name: `excludedDirs` adds `testdata`, `__tests__`, `e2e` and `examples`; `testFileWords` adds `e2e`, for files with such a word in their name (`spec` counts only after the first word, since a manifest may be called `spec.yaml`); and a name whose first word is one of `testWords` is held back after attribution, so the report lists the unit's held-back names and the drop is never silent. Holding back is a drop, not a demotion, because ranking has no weight to demote by; `--term` never goes through the rule, so it is the way to send such a name. A directory on the path to the one discovery was asked about is never excluded, so `examples/checkout` still discovers. `dev` is deliberately not excluded: it names an environment, and an overlay for it describes exactly what runs on the environment developers use most. The disclosure is the plan itself: `PlanDiscovery` needs no network, and `--dry-run` prints its exact output and returns before a client is built, so it works with no token and in any safety level.

### Names that are not the unit's own

A repository holds names of things that are not its code, and they reach the queries like every other name: they are how a candidate is found. Found is not settled, and a `match` with a line to run must rest on more than a file that happens to be in the checkout. So every name carries whether the unit gives it to itself, and a candidate matched only by names that it does not (`Candidate.Indirect`, the reason in words) is never a `match`, for the report or for a kind, and gets no `set` line in any output: the line is the whole hand-off, and nothing shows that the candidate runs this code. `indirectNames` in `extract.go` is the rule:

- **The unit's own:** a build file's name, a Dockerfile's entrypoint, the unit's directory or the directory discovery ran for, and a `--term`.
- **An image is never the unit's own.** A manifest lists the images of sidecars and of the products deployed beside the service, and an image of the service itself is named by something else as well.
- **The origin remote's name is not, alone.** It is often an organisation's or a platform's name for everything in the repository.
- **A manifest or chart counts when the unit claims it by name:** its workload, one of its images or the chart is called what a build file, the unit's directory or the remote calls the unit. Its workload name and `OTEL_SERVICE_NAME` are then the unit's own, whatever they are. A manifest nothing claims may deploy a cache, a broker or a proxy, and `deploy/redis.yaml` in the `checkout` repository is the case this exists for. The remote counts here because two independent sources then agree: the repository's name and a manifest inside it.
- **Nothing at or below a directory the walk skips or excludes is,** the directory's own name included: `vendor`, `node_modules` and build output hold other projects' names, and being asked about `testdata/fixtures/payments` or `examples/checkout` does not make a fixture or a demonstration the service. Those directories are still read when discovery is asked about one, as before; what changed is what their names can prove.

The way out is the one that already existed for a name discovery does not trust: `--term`. A term is the user's statement that the name is this code's, so it stands beside a file's token of the same spelling as evidence of its own, and the note on a candidate without a line names the term that confirms it (`repoScopeConfirmHint`). A service-name line that would select several candidates is withheld only when every candidate reporting the name was found indirectly.

The rule errs towards asking. A single-service repository whose only manifest deploys it under a name no build file spells is `ambiguous` until a term confirms it; the rule cannot tell that manifest from a dependency's, and the one that proposes less is the one that is never wider than the evidence. Not covered: a nested checkout or submodule (follow-up 21), and a third-party build file outside the skipped and excluded directories.

### Never writes

`discover` has no prompt, no state store and no `--save`. It prints, per candidate, the `dtctl repo-scope set …` line that saves it, and the agent envelope carries the same line as `result[].candidates[].setCommand` (the result is a list of reports, one per unit, also when there is one, so a reader has one shape to handle), and for a `match` also as the first of `context.suggestions`, prefixed "confirm with the user"; for anything less the suggestion is to show the candidates and ask. Running `set` is the confirmation. This keeps the one decision that changes what every later query returns with a person, and it means the command an agent proposes is the command a human can read, check and run.

Because the line is the whole hand-off, it has to save exactly the candidate shown, with nothing carried over but the line:

- **Environment.** `set` files under the current context's host, so the line always carries `--context`, the config's current one included: that is the context a `dtctl ctx` changes while the line is still on the screen or in an agent's transcript. It carries `--config` when something other than the default chose the config file, the flag or `DTCTL_CONFIG`: the variable may be set for one command as the flag is, and the line may be run in a shell that does not have it.
- **Directory.** A unit below the root is a build unit, so the line carries `--path <unit>`. The root is also the unit of every directory without a build file, and there the directory alone does not say whether it is a service: in a monorepo with one build file at the top, `services/ledger` is the ledger, while in a single-module repository `internal/handlers` is one package of the service its `go.mod` names. Its name decides. When the name of the directory discovery ran for (`Plan.Dir`) is among what matched a candidate (`Candidate.MatchedDir`), the line carries `--path` for that directory, so the sibling service can be linked next; otherwise it covers the whole repository. The lines for linking by hand have no candidate to decide by, so they carry the unit's `--path` and say how to cover only the directory.
- **Bindings.** The line binds the workload, with its cluster, or for a candidate no workload binding describes, the service name; the bindings are alternatives, so each must select only the chosen candidate, and a service name beside a workload would select that name in every cluster and namespace, now and for whatever is deployed under it later. A service name another candidate also reports, from another namespace or another workload such as a canary (`Candidate.ServiceNameShared`), would also select that one, so it is left out, with one line saying why. Entity ids are proposed only when neither remains, since both fields are deprecated, with one exception: a candidate whose logs discovery found by its process groups and not by its names gets `--process-group` beside the workload, because the alternative is an entry that silently returns no logs. That id comes from a whole, uncapped read, as every proposed id does. What discovery could not check, it does not bind: a service name is on the line only when it is a name that was sent, since the queries compare `service.name` to those alone; a partial or sampled result binds the workload only, the cluster being a key the rows were grouped by and everything else something an unseen candidate could share; and ids are bound only when no other candidate carries one, when they reach every data object the candidate was found in (spans by service id, logs by process group), and when the candidate matched exactly or by a segment (`repoScopeIDRefusal`). A candidate nothing selects alone gets no line. A match with no line falls back to the narrowing hint and the lines for linking by hand; an ambiguous report where no candidate has a line says nothing tells them apart and offers the shared service name, labelled as selecting all of them.

### Verdicts

Candidates are keyed by cluster, namespace, workload and service name, so the result does not depend on the order rows arrive in. They rank by tier (exact > segment > substring), then by how many distinct repository sources named them, then by records, or a sample's hits, per hour, so a candidate read over an hour compares with one read over a day. A verdict is computed per kind of binding (service, process group, workload, service name) and overall: `match` is exactly one exact-tier candidate found in records read whole and matched by a name of the unit's own (see [Names that are not the unit's own](#names-that-are-not-the-units-own)), `ambiguous` is several, a partial or sampled result, one that only indirect names matched, or one that rests on the entity-name fallback alone (an entity outlives its last record, so a name in the entity table is not evidence that the code runs), `none` is none. A failed, timed-out, cancelled or capped query marks the report partial, so `none` is never read as "nothing runs this code" when the answer was incomplete. A query whose page is as long as its own `limit 200` counts as capped (`row_limit`), as does one Grail reports as truncated. Per-kind verdicts count distinct ids, from the id count where a candidate has one, so two process groups on one candidate are `ambiguous` for that kind and so is a candidate listing one of its 200 service ids. A kind is never `match` unless the overall verdict is: the one service name of two candidates is what they share, not something settled. The workload kind tells clusters apart by the uid the records carry, whether or not a scope file could hold it, and has no value for records that name a workload without a namespace. A sampled rung that finds a candidate is complete at the floor its note states (about three times the ratio, at roughly 95% confidence), so the report is not partial, but it is never a `match`, overall or for a kind: what sits below the floor could be a second candidate, which is the reason the set line already withholds the service name. One that finds none is partial, because a sampled miss is a bound, not an absence. A sampled candidate carries the hits its sample matched (`spansSampled`, `logsSampled`), which the sampled query counts with `count()` as the whole one does, and ranks on them per hour, never on an extrapolated population: on a large environment the extrapolation came out hundreds of times above the true rate. A sampled candidate's set line binds the workload only: shared-service-name detection is unreliable below the floor, and its ids are only the sample's. Once any record query was sampled, no candidate's line carries `--service-name`, whether its own records were sampled or not: the candidate that would share the name may be the one below the floor.

## Decisions

1. **Default scoping applies in every mode, CI and agent mode included.** The file is committed and reviewed like code, it can only narrow a query, every scoped run prints the notice, and a scoped run that returns nothing prints the zero-rows hint pointing at `--no-repo-scope`. A CI job that wants the whole environment sets `DTCTL_NO_REPO_SCOPE=1` once. A notice-only mode for non-interactive runs would make the scope do nothing in exactly the runs nobody watches.
2. **No trust fingerprinting.** dtctl does not record which scope files a user has accepted. The file cannot widen or redirect a query, and the notice names the filter it applied; a trust store would be a second trust model next to "reviewed like code" for no additional protection.
3. **No ownership or permission checks on the repository root.** The walk-up requires `.git`; a world-writable checkout is a problem for every file in it, not for this one.
4. **No lock for concurrent `set`, at the cost of a lost entry.** The write is a temp file, fsync and rename, so a reader never sees half a file and the last writer wins. Two `set` runs that overlap both load the old file, both report success, and the entry of the one that renamed first is gone; a `delete` of the last entry it read removes a file another run has just added an entry to: the file stays valid and the loss shows only in `git diff`. That is a known loss, accepted for the first release because one person edits a checkout at a time, and it is listed under the follow-ups with its cure. The rename is atomic on POSIX systems; on Windows `os.Rename` replaces the file with `MoveFileEx`, which can fail while another process holds it open (the old file then stays in place and `set` reports the error) and is not documented as atomic.
5. **No set-time applicability probe.** `set` sends nothing. Whether the records carry the bound fields is what discovery checks before it proposes an id, and the zero-rows hint covers bindings written by hand.
6. **CLI only.** The working directory and the scope file are host state. `repo-scope` is in the engine's `unsupportedCommands`, and `currentWorkDir` refuses an invocation without `HostWorkingDirectory` or with a session, so a service request never resolves a scope even when the host process happens to run inside a checkout. `TestEngineOutputEqualsCLI` runs its CLI side in a temporary directory for the same reason.
7. **`.dtui.yaml` is not read.** See [dtui's workspace file](#dtuis-workspace-file): dtctl leaves the workspace file to dtui, and dtui, which does not read the scope file yet, is meant to consume it through `pkg/reposcope` rather than a parser of its own.

12. `get snapshots` after a re-version (hit limit, update) reads only the current immutable id. Earlier ids cannot be recovered: snapshots carry only `breakpoint.id`, the rule API returns `revision_count` but no ids, and ids are a tenant-wide sequence. Until then the hint `get snapshots` prints for an empty result keys on the disable reason only: it is not qualified by the timeframe or by a partial scan, an enabled breakpoint that was re-versioned gets none, and it offers `--no-repo-scope` also where a stability floor refuses the flag.
13. A lock around `set` and `delete`, so that of two runs at once neither loses its entry (decision 4): `pkg/usage` has a file lock to share.
14. `set` and `delete` keeping comments, key order and hand formatting. The reader already works on the YAML node tree; the writer would edit that tree in place, as the config writer in `sdk/session` does, where today it encodes the whole file anew.
15. Path matching on a case-sensitive macOS volume. Paths are compared with case folded on macOS and Windows, which is right for their default volumes; on a volume formatted case-sensitive an entry for `services/Checkout` also covers `services/checkout`. Composition is the same case on every system: paths are compared in NFC, so on a filesystem that keeps both spellings (Linux) an entry for a directory also covers a sibling whose name differs only in composition. Deciding per volume needs a probe of the filesystem the repository is on.
16. Exported functions to validate and to decode a scope file from bytes, for a consumer that reads it from somewhere other than the host disk or that writes one itself. Additive, and waiting for such a consumer.
17. `RepoFS` on `os.Root`, so that no read through it can follow a symbolic link out of the repository. Today each reader refuses links itself: the scope file and the build files are read only as regular files, the walk does not descend a link, and `set --path` and `discover --path` refuse one by name.
18. The Go API split in two packages, reading a scope and discovering one (see [The Go package](#the-go-package)).
19. dtui applying the scope file to its logs and spans views through `pkg/reposcope`, once a release carries the package. Reporting a checkout's `.dtui.yaml` in `repo-scope describe` (its segments as `--segment` flags, its environment against the context's) and an opt-in query flag for those segments wait for dtui to agree on a shared parser for that file.
20. Moving the search inside workload names behind "the exact names found nothing". Today the `contains` clause sits in the two record queries, before the aggregation, so every repository pays for the scan of whatever else holds its name, and a busy workload that merely contains the name can push an exact match over the scan cap (the exact rows are then still kept, and the run falls back to a sample). Run as queries of their own, like the entity fallback, the clause would cost a prefixed workload two more queries and an exact match nothing. Which is cheaper is unmeasured: decide after comparing both forms on one large environment.
21. The walk enters nested checkouts and submodules: it skips `.git`, not a directory that holds one, so another repository's manifests can name this one's unit.
22. A directory N Gradle deployables share is walked N+1 times, once to find the deployables and once for each plan. The caps bound each walk and N is small; one walk shared by the plans would remove the repetition. Nothing bounds how many deployables one run discovers for either: each has its own walk, ten queries, sixty seconds and disclosure line, so a count past which the command asks for `--path` belongs with the shared walk. In the same pass: build the map from entity id to the candidates that carry it once per report (`repoScopeIDRefusal` scans every candidate for every candidate), refuse a plan of more than 200 values before `heldBack` runs, and take the claim loop out of modules times claims.
23. The Gradle reader's known wrong guesses: a `project(...)` reference that only reads a property such as its version, a test dependency declared over several lines, a deployed root project, a `projectDir` remap, and block comments. The word lists it and the walk rely on (`stopWords`, `layoutWords`, `testWords`, the skipped directories) are kept by hand; `build` among the skipped directories hides Go's `build/package/Dockerfile`.
24. The entity search keeps the 200 shortest names, so 200 short matches of one name can cut an exact long one. A full page already caps the verdict at `ambiguous`.
25. A workload whose spans carry two service names is two candidates, and a logs row without a cluster beside them joins neither. The cure is a candidate keyed by workload that lists its service names, which reshapes the report, the set line and the goldens. 27. 43.
